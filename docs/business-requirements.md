# Бизнес-требования — «Учёт товара магазина»

Документ описывает бизнес-требования к учебной системе складского учёта магазина:
что система должна делать, для кого, по каким правилам и как проверяется результат.

- **Версия:** 1.0
- **Статус:** учебный проект
- **Связанные документы:** [README](../README.md), [UML-диаграммы](diagrams/)

---

## 1. Цель проекта

Магазин закупает товар у разных поставщиков и продаёт его. Часть товара списывается
из-за истечения срока годности или порчи. Сотрудникам нужен единый учёт, который
показывает фактический остаток, себестоимость запасов и реальную прибыль по каждому
товару за выбранный период.

**Цель системы** — автоматизировать учёт поступлений и списаний, обеспечить партионный
учёт товара и предоставить отчёты, необходимые для управления закупками, ценами и сроками
годности.

### Что входит в проект

- справочники товаров и поставщиков;
- документы поступления и списания;
- партионный учёт с разными закупочными ценами;
- расчёт прибыли с учётом себестоимости и налога;
- отчёты по остаткам и срокам годности;
- веб-интерфейс и REST API;
- демонстрационные данные для проверки.

### Что не входит в проект

- бухгалтерский и налоговый учёт в полном объёме;
- интеграция с кассовым оборудованием и маркетплейсами;
- разграничение прав доступа и аутентификация;
- управление заказами поставщикам и логистикой;
- полноценный production-контур развёртывания.

## 2. Участники и роли

| Роль | Цели | Основные действия |
|---|---|---|
| **Кладовщик** | Принять товар и отразить движение запасов | Оформляет поступления, продажи, списания по сроку годности и порче, смотрит остатки |
| **Менеджер** | Контролировать прибыль и сроки годности | Смотрит отчёты о прибыли, просроченных списаниях и товарах с истекающим сроком |
| **Администратор** | Поддерживать справочники | Добавляет товары и поставщиков |
| **Поставщик** | Передать товар магазину | Внешняя сторона: поставляет товар, в системе не работает |

В демонстрационной версии роли логические: интерфейс не ограничивает действия по ролям.

## 3. Бизнес-требования

| ID | Бизнес-требование | Приоритет | Как реализовано |
|---|---|---|---|
| **BR-01** | Магазин должен учитывать поступления товара от разных поставщиков | Высокий | `Supplier`, `Receipt`, `ReceiptItem`; интерфейс «Поступления» |
| **BR-02** | Один и тот же товар может поступать по разным закупочным ценам, поэтому учёт должен вестись по партиям | Высокий | каждая приёмка создаёт `ReceiptItem` со своей `UnitCost` |
| **BR-03** | Магазин должен фиксировать списания товара с причиной: продажа, истечение срока годности, порча | Высокий | `WriteOff`, `WriteOffItem`, `WriteOffReason` |
| **BR-04** | При продаже должна фиксироваться цена реализации, а себестоимость — по фактической партии | Высокий | в `WriteOffItem` сохраняются `UnitCost` и `UnitSalePrice` |
| **BR-05** | Списание должно автоматически распределяться по партиям, начиная с той, у которой раньше истекает срок годности | Высокий | алгоритм FEFO в `InventoryService` |
| **BR-06** | Менеджер должен получать отчёт о прибыли за период: по каждому товару и итого, с учётом себестоимости и налогов | Высокий | `GET /api/reports/profit` |
| **BR-07** | Менеджер должен видеть товары, списанные по истечении срока годности, и сумму потерь | Высокий | `GET /api/reports/expired-write-offs` |
| **BR-08** | Менеджер должен заранее видеть товары с истекающим сроком годности | Средний | `GET /api/reports/soon-to-expire?days=7` |
| **BR-09** | Кладовщик должен видеть актуальные остатки и стоимость запасов | Средний | `GET /api/reports/stock` |
| **BR-10** | Система должна быть готова к проверке без ручного заполнения данных | Средний | автоматическое создание SQLite и демо-данные `DbSeeder` |

| **FR-12** | Сводный отчёт по остаткам | — | остаток и стоимость по каждому товару |
| **FR-13** | Показатели главного экрана | — | остаток, выручка, прибыль, потери, число срочных позиций |

## 5. Бизнес-правила

| ID | Правило |
|---|---|
| **BR-R-01** | Дата поступления и дата списания не могут быть в будущем |
| **BR-R-02** | Количество в любой строке должно быть больше нуля |
| **BR-R-03** | Закупочная цена не может быть отрицательной |
| **BR-R-04** | Срок годности не может быть раньше даты поступления |
| **BR-R-05** | Для продажи цена реализации обязательна и должна быть больше нуля |
| **BR-R-06** | Один товар не может повторяться в одном документе списания |
| **BR-R-07** | Продажа использует только непросроченные партии |
| **BR-R-08** | Списание по сроку годности использует только партии с истёкшим сроком |
| **BR-R-09** | Порча может списываться из любых партий |
| **BR-R-10** | При недостатке остатка операция отменяется полностью, частичное списание не допускается |
| **BR-R-11** | Себестоимость и цена продажи фиксируются на момент списания и не меняются задним числом |
| **BR-R-12** | Налог рассчитывается от выручки по ставке, заданной в настройках или запросе (по умолчанию 6%) |

### Формулы отчёта о прибыли

```
Выручка         = Σ (Количество × Цена реализации)
Себестоимость   = Σ (Количество × Закупочная цена партии)
Валовая прибыль = Выручка − Себестоимость
Налог           = Выручка × Ставка налога
Чистая прибыль  = Валовая прибыль − Налог
```

## 8. Критерии приёмки

Проект считается соответствующим требованиям, если:

- [x] можно создать поставщика, товар и поступление;
- [x] один товар можно принять несколькими партиями с разными ценами;
- [x] продажа уменьшает остаток и фиксирует себестоимость партии;
- [x] при недостатке остатка возвращается ошибка `400`, остаток не меняется;
- [x] списание по сроку годности невозможно без просроченных партий;
- [x] отчёт о прибыли показывает выручку, себестоимость, налог и чистую прибыль по товарам и итого;
- [x] отчёт по просроченным списаниям показывает количество и сумму потерь;
- [x] отчёт по срокам годности показывает товары, которые скоро испортятся;
- [x] остатки и стоимость запасов совпадают с данными партий;
- [x] интерфейс позволяет выполнить основные операции и посмотреть отчёты;
- [x] проект запускается на чистой базе и сам создаёт демо-данные.

## 10. Допущения

- проект учебный, поэтому аутентификация и роли не реализованы;
- налог считается упрощённо — с выручки по единой ставке;
- интерфейс создаёт документы по одной строке, API поддерживает несколько строк;
- SQLite выбрана для простоты запуска; при переходе на другую СУБД меняется провайдер EF Core;
- схема создаётся через `EnsureCreated()`, миграции не используются.
